## 1. 体制

| 役割 | だれ | すること |
|---|---|---|
| 管理者 | 開発者（kazuyuki-a-dev）1人 | 報告の確認と対応、毎月の点検、鍵の管理、障害の対応、バックアップから戻す |
| 利用者 | 会員 | 不適切な投稿やまちがった情報を、カルテ・釣行詳細の「報告」から知らせる。現地の情報を直す |

- 管理者は1人なので、休むときは README の「お試し環境」に止めている間のことを書く（新しい報告への対応が遅れることがある、など）
- 管理者を足すときは `php artisan app:make-admin メールアドレス`（画面からは管理者になれない）

## 2. 毎月の点検（毎月の初めに1回）

チェックリストを上から順に見て、結果を GitHub の Issue に1つ残します（タイトル例：「2026年11月の点検」。全部問題なければ、本文に「すべて問題なし」と書いて閉じる）。

| # | 見ること | どこで | 問題があったら |
|---|---|---|---|
| 1 | 毎日のバックアップが、この1か月すべて成功している | GitHub の [Actions → バックアップ](https://github.com/kazuyuki-a-dev/fishing-log/actions/workflows/backup.yml) | 「5. 障害のとき」の「バックアップが失敗した」 |
| 2 | いちばん新しいバックアップの Summary で、本番と戻したものの件数が一致している | 同じ画面の最新の実行の Summary | 同上 |
| 3 | R2 の `fishinglog-backups` の `db/` に、30日より古いファイルが残っていない | Cloudflare の R2 | ライフサイクルのルール `db-30days` を見直す |
| 4 | 写しにだけ残っている写真（退会や削除で消した写真）を消す | 手元のパソコン（[`docs/backup.md`](backup.md) の「退会した人の写真」） | — |
| 5 | テストのメールを1通送って届く（Brevo の SMTP キーは90日使わないと切れるため、毎月使って防ぐ） | お試し環境のログインの画面の「パスワードを忘れた方」に、自分の確認用の会員のアドレスを入れる | 「5. 障害のとき」の「メールが届かない」 |
| 6 | 死活監視で、この1か月に止まった時間がない（あれば、原因をログで見る） | UptimeRobot のダッシュボード | 「5. 障害のとき」の「開かない」 |
| 7 | GitHub Actions のテストが main で成功している（README のバッジが緑） | GitHub の [Actions → テスト](https://github.com/kazuyuki-a-dev/fishing-log/actions/workflows/tests.yml) | 失敗したテストを直す Issue を作る |
| 8 | Dependabot の PR と、弱点の知らせ（alerts）が残っていない | GitHub の Pull requests と Security | CLAUDE.md の「Dependabot の PR が来たとき」の手順で対応 |
| 9 | 管理画面の未対応の報告が0件（3日を過ぎたものがない） | お試し環境の管理画面 `/admin/reports` | 「3. 投稿と現地の情報の確認」 |
| 10 | 鍵の期限が近くない（下の「4. 鍵と期限の管理」の表） | この手順書の表 | 期限の1か月前までに作り直す |
| 11 | Render の無料の時間・Aiven・R2 の使用量が、無料の枠に収まっている | Render：ワークスペースの Billing（無料のインスタンス時間 月750時間）／Aiven：fishinglog-db の Overview（ディスク 1GB）／R2：R2 のトップ（保存量 10GB・Class A 月100万回・Class B 月1000万回） | 収まらなくなりそうなら [`docs/release-plan.md`](release-plan.md) を見て、プランを考える。**Render は1つのサービスを24時間動かすと月744時間で、750時間の枠にほぼいっぱい**。同じワークスペースで無料のサービスを増やさない |

## 3. 投稿と現地の情報の確認

### 報告を受けたとき

- **期限：報告から3日以内に確かめる**（管理画面の「未対応」を「確認済み」以上にする）
- ただし、次の **急ぎのもの** は、気づいたらすぐに非表示にする
  - 個人を特定できる情報（本名・電話番号・住所・顔がはっきり写った他人の写真など）
  - 立入禁止・釣り禁止の場所や私有地を、釣れる場所として案内しているもの
  - 命にかかわる危険を招く情報（危ない足場を「安全」と書く、など）
- 報告はナビの付箋「報告 N」（N は未対応の件数）と、管理画面 `/admin/reports` で見る。メールでは知らせないので、毎月の点検とは別に、**2〜3日に1回は管理画面を開く**

### 対応の基準

| 報告の理由 | 確かめること | すること |
|---|---|---|
| 不適切な内容 | 利用規約に合わない内容か（悪口・宣伝・関係のない写真・個人情報など） | 合わなければ **非表示**（公開範囲を非公開にする。消さない）。投稿した人には知らせない |
| 誤った釣り場情報 | 位置・名前・現地の情報がまちがっているか。地図・公式の案内・現地の写真で確かめる | 現地の情報なら、正しい値に **直す** か、変更の履歴から **前の値に戻す**。名前や位置なら、釣り場を登録した人に直してもらう（直らなければ非表示） |
| 危険を招く情報 | 立入禁止・釣り禁止・危ない足場などを、安全・釣れる場所として案内していないか | 急ぎとしてすぐ **非表示**。現地の情報の注意区分を「立入注意」などに直す |
| その他 | 中身を読んで、上のどれに近いかで判断する | 上と同じ |

- 対応したら、管理画面で対応状況を「対応完了」にする（非表示にすると、その投稿への報告はまとめて対応完了になる）
- 判断に迷ったら非表示にしておき、確かめられてから公開に戻す（公開範囲を戻すのは投稿した本人。管理者は戻さない）
- 判断の記録は管理画面の報告に残る。基準を変えたら、この手順書の版を上げる

### 現地の情報が書きかえられたとき

- 現地の情報（駐車場・トイレなど）は、見られる人みんなで直せる。カルテの「変更の履歴」と、すべての履歴のページ `/spots/{番号}/history` に、だれが・いつ・何を何に変えたかが残る
- まちがった変更やいたずらを見つけたら、管理者として履歴のページの **「この変更の前に戻す」** を押す（戻したことも履歴に残る）
- 同じ人が何度もいたずらをするときは、その人の投稿を非表示にし、利用規約にもとづいて対応を考える（今はアカウントを止める機能はない。[`docs/release-plan.md`](release-plan.md) の項目）

## 4. 鍵と期限の管理

鍵（パスワードや API キー）は **1年に1回、毎年10月にまとめて作り直す**。会話・画面・ログなどに出してしまったときは、**その場ですぐ作り直す**。

| 鍵 | どこで作る | どこに入れている | 期限 | 作り直すとき |
|---|---|---|---|---|
| Brevo の SMTP キー | Brevo → SMTP & API → SMTP | Render の `MAIL_PASSWORD` | 2027-10-23。**90日使わないと切れる** | 新しいキーを作って Render に入れ、テストのメールが届いたら古いキーを消す |
| R2 の鍵（アプリ用） | Cloudflare → R2 → API tokens | Render の `AWS_ACCESS_KEY_ID`・`AWS_SECRET_ACCESS_KEY` | 決めていない（自分で毎年作り直す） | 新しい鍵を作って Render に入れ、写真が表示・保存できたら古い鍵を消す |
| R2 の鍵（バックアップ用 `fishinglog-backup`） | 同上 | GitHub の Secrets `BACKUP_R2_*` | 同上 | 新しい鍵を作って Secrets に入れ、Actions → バックアップ → Run workflow で成功したら古い鍵を消す |
| Aiven のパスワード（`avnadmin`） | Aiven → fishinglog-db → Users → Reset credentials | Render の `DB_PASSWORD` と GitHub の Secrets `BACKUP_DB_PASSWORD` | 決めていない | 作り直すと古いパスワードはすぐ使えなくなるので、**Render と GitHub の両方をすぐに入れかえる**。お試し環境が開くこととバックアップの成功を確かめる |
| APP_KEY（アプリの暗号の鍵） | `php artisan key:generate --show` | Render の `APP_KEY` | なし | 作り直すとログインしている人が全員ログアウトされる。漏れたときだけ作り直す |
| ADMIN_PASSWORD（管理者のパスワード） | 自分で決める | Render の `ADMIN_PASSWORD`（お試しデータを入れ直すとき） | なし | 管理者でログインして、プロフィールから変える |

- 鍵の値は、Git・Issue・PR・会話・Notion に書かない。確かめるときは `***` に置きかえる
- 作り直した日は、この表の「期限」の欄を直して版を上げる

## 5. 障害のとき

### お試し環境が開かない

1. UptimeRobot から「Down」のメールが来ているか、Render の **Events** に失敗が出ていないかを見る
2. Render の **Logs** を見る
   - 「データベースの住所が見つからない（getaddrinfo … failed）」→ Aiven の `fishinglog-db` が **Powered off** になっていないか。なっていれば **Power on**（データは残る）
   - 「needs attention」・起動の失敗 → 直前の main への push が原因のことが多い。GitHub の main の最新のコミットと Actions のテストを見て、直すか `git revert` で戻して push する
3. 直ったら、お試し環境を開いて、ログイン・カルテ・写真が表示されることを確かめる

### メールが届かない（確認のメール・パスワード再設定）

1. 画面に「今はメールを送れませんでした」「今は確認のメールを送れませんでした」と出たら、Render の **Logs** で「パスワード再設定のメールを送れませんでした」「確認のメールを送れませんでした」の行を見る
   - `Connection could not be established` / `timed out` → `MAIL_PORT` が **2525** か（Render の無料のプランは 587 番が止められている）
   - `Authentication failed` / `535` → Brevo の SMTP キーが切れたか消えた。「4. 鍵と期限の管理」で作り直す
2. 画面には「送りました」と出るのに届かない → 迷惑メールのフォルダを見る。Brevo の **Transactional → Logs** で、送れたか・はねられたかを見る
3. 利用者から「確認のメールが届かない」と知らせがあったら、確認の画面の「確認のメールをもう一度送る」と、迷惑メールのフォルダを案内する。アドレスをまちがえていたら、プロフィールで直してもらう（確かめる前でもプロフィールは開ける）。管理者が代わりに確認済みにすることはしない（本人のアドレスか分からないため）

### バックアップが失敗した

- GitHub から「Run failed: バックアップ」のメールが届く。直し方は [`docs/backup.md`](backup.md) の「失敗したとき」

### データを消してしまった・壊してしまった

- [`docs/backup.md`](backup.md) の「本番に戻す手順」（データベース・写真）。戻す前に、必ず今の状態もバックアップする

### 障害のあとに残すこと

- 何が起きたか・原因・直し方・同じことを防ぐためにしたことを、GitHub の Issue に残す（実務の「障害報告」）。防ぐための直しがあれば、その Issue から PR を作る

## 6. 外部サービスの一覧

| サービス | 何に使っているか | 入れる人 | 無料の枠の決まりで気をつけること |
|---|---|---|---|
| GitHub | プログラムの置き場所・テストとバックアップの自動実行（Actions）・Dependabot | 開発者 | 60日間リポジトリに変更がないと、定期の Actions が止まる |
| Render | アプリを動かす（main に push すると自動で公開し直す） | 開発者 | 15分使われないと止まる（UptimeRobot で起こしている）。SMTP の 587 番は使えない |
| Aiven | MySQL のデータベース | 開発者 | 使われていないと止められる（Powered off）。Event log の時刻は UTC |
| Cloudflare R2 | 写真・バックアップの置き場所 | 開発者 | 10GB まで。消した写真を戻すしくみはない（バックアップで守る） |
| Brevo | 会員登録・メールアドレスの変更のときの確認のメールと、パスワード再設定のメールを送る（SMTP） | 開発者 | 1日300通まで。送り主は無料の Gmail なので、迷惑メールに入ることがある |
| Gmail（fishinglog.dev@gmail.com） | メールの送り主・Brevo の確認のメール | 開発者 | 2段階認証を入れておく |
| UptimeRobot | 死活監視（5分おきに `/spots` を開く） | 開発者 | — |
| MET Norway・Open-Meteo | 天気予報・釣行の天候 | （登録なし） | Open-Meteo は1日の回数の上限で断られることがある（そのときは空のまま保存） |
| OpenStreetMap | 地図の画像 | （登録なし） | 帰属表示を出す |

### 止まらないしくみと、起動時の処理

- 無料の枠は、しばらく使われないとアプリやデータベースが止まる。UptimeRobot で5分おきに `/spots` を開いて止まらないようにしている（止まったときは知らせが届く）。予備として、GitHub Actions でも3時間に1回開いている（`.github/workflows/keep-alive.yml`）。本番で使うときは、止まらない有料のプランにする（[`docs/release-plan.md`](release-plan.md) の項目 1・2）
- 起動のたびに、マイグレーションとお試しデータの準備をしている（`docker/start.sh`）。複数のインスタンスで同時に起動しても重ならないように、マイグレーションは `--isolated`、お試しデータの準備はロック（`demo-data`・`sample-photos`）で1つずつ動かしている。規模を広げるときは、デプロイのときに1回だけ動く処理（Render の Pre-Deploy Command など）に分ける（[`docs/release-plan.md`](release-plan.md) の項目 6）
